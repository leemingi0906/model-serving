## 1. 이해관계자 가치 (Pain Point)

수업 첫 시간에 교수님이 하신 말 중에 제일 남은 게 "3개월 박수"였다. 데이터 사이언티스트가 공장에 들어가서 모델 잘 만들어 놓으면 딱 3개월 박수받고, 3개월 지나면 안 맞는다고 전화 오고, 가면 혼난다는 얘기. 처음엔 웃었는데 Day3에 드리프트 배치 넣어보고 나니까 그게 그냥 농담이 아니었다. 서버는 멀쩡히 200을 내는데 값만 틀린다. 교수님 표현대로 "AI는 에러 없이 틀린다".

### 1-1. 모델이 노트북에만 있을 때 (Day1)

| 이해관계자 | 서빙이 없으면 |
|---|---|
| 사용자(투자 분석가) | 예측값이 필요할 때마다 데이터 과학자한테 부탁해야 한다. |
| 운영자 | 모델이 떠 있는지 알 방법이 없다. 사용자가 먼저 발견한다. |
| 모델 개발자 | 학습 때랑 다른 형태의 입력이 들어와도 막을 데가 없다. |
| 경영진 | 학습에 돈 썼는데 서비스에 안 붙어 있으니 얻는 게 없다. |

직접 겪은 걸로 적으면, Day1에 Lazy로 서버를 띄웠더니 모델 파일이 없는데도 `/health`가 `status: ok`였다. 운영자가 그것만 보고 있었으면 장애를 몰랐을 것이다. 서버가 살아 있는 것과 예측할 준비가 된 것은 다른 얘기다. 이 차이가 Day1에서 제일 크게 와닿았다.

### 1-2. 모델을 바꿔 배포했는데 뭐가 바뀌었는지 모를 때 (Day2)

Day2에서 `train_and_register.py`를 돌렸더니 콘솔에 `HAIC_Predictor v1`이 찍혔다. 그런데 클라우드에서 다시 돌릴 때는 이전 세션 기록이 남아 있어서 v3부터 시작했다. 내가 지금 서빙 중인 게 몇 번째 버전인지 기록이 없으면 본인도 헷갈린다는 걸 직접 겪었다.

| 이해관계자 | 버전 관리와 게이트가 없으면 |
|---|---|
| 모델 개발자 | 어떤 실험이 더 나았는지 기억에 의존한다. |
| 운영자 | 방금 배포한 모델이 전보다 나은지 모르는 채 트래픽을 받는다. |
| 경영진 | 성능 나쁜 모델이 실수로 나가는 걸 막을 장치가 없다. |

### 1-3. 모델이 조용히 나빠질 때 (Day3)

Day1, Day2는 뭔가 안 되면 에러가 났다. Day3는 다르다. 드리프트 배치를 넣었을 때 서버 로그 어디에도 에러가 없었다. `drift_check`의 RMSE 값만 커졌다. 그리고 재학습이 돌았다는 로그와 서빙에 반영된 것은 또 다른 일이라는 걸 4-7의 버그로 알았다. `[OK] production promoted`가 찍혔는데 `/predict`는 그대로였다. 로그만 보고 됐다고 판단했으면 아무것도 안 바뀐 서비스를 계속 운영하고 있었을 것이다.

| 이해관계자 | 모니터링과 드리프트 감지가 없으면 |
|---|---|
| 사용자 | 모르는 사이에 틀린 예측으로 의사결정한다. |
| 운영자 | 항의가 쌓이기 전까지 모른다. |
| 모델 개발자 | 언제부터 나빠졌는지 나중에 로그를 뒤져서 역추적해야 한다. |

조별 과제에서는 이걸 태양광 발전소로 바꿨다. 전력중개사업자는 매일 아침 10시 전에 다음 날 24시간 발전량을 제출해야 하고, 오차가 크면 그날 정산을 못 받는다. 여기서 Pain Point가 하나 더 생겼다. 오차가 커졌을 때 그게 날씨 탓인지 설비 고장인지 모델이 낡아서인지 모른다는 것. 이건 HAIC에는 없던 문제였다.

## 2. 이를 해결하기 위한 AI 솔루션

교수님이 "와이어링"이라는 말을 계속 쓰셨다. 머신러닝, 딥러닝, 백엔드, 프론트, 랭체인 다 따로 배웠는데 그걸 선으로 이어서 운영되게 만드는 게 AIOps라고. 3일 실습이 딱 그 와이어링이었다.

| Day | 기술 | 역할 | 내가 확인한 것 |
|---|---|---|---|
| 1 | FastAPI 라우터, Pydantic 스키마 | 모델을 API로 감싸고, 학습 때랑 같은 모양의 입력만 통과시킨다 | 19개·close≤0은 모델에 닿기 전에 422 |
| 1 | /health, Lazy/Eager | 서버 상태와 모델 로딩 여부를 밖에 알리고, 로딩 비용을 언제 낼지 고른다 | 3-1 측정표 |
| 2 | MLflow Tracking | 학습마다 파라미터·RMSE·모델 파일을 기록한다 | log_param, log_metric("rmse") |
| 2 | Model Registry, 배포 게이트 | RMSE ≤ $4를 통과한 버전만 Production으로 올린다 | `[GATE PASSED] rmse=2.03 -> v1` |
| 2 | _load_from_mlflow() | 서버가 버전 번호가 아니라 Production 단계를 바라보게 한다 | model_version이 production-v1 |
| 2 | Dockerfile, docker-compose | 의존성과 학습·등록 과정을 이미지에 고정한다 | 컨테이너에서 같은 RMSE, 같은 응답 |
| 3 | drift_detector.py | 최근 21건 RMSE를 $4와 비교한다 | 정상 ok, 드리프트 재학습 |
| 3 | retrain_trigger.py | warm start fine-tuning, 게이트 재검증, 승격, 캐시 비우기 | WARN, INFO, OK 로그 |
| 3 | simulate_drift.py | 정상 변동성과 3배 변동성을 재현해 루프를 검증한다 | send_batch 구현 |

수업에서 "FastAPI는 모델 서빙용으로만 쓴다"는 것도 처음 알았다. 파이썬은 컴파일이 안 돼서 컨테이너를 열면 코드가 다 보이고, 패키지 버전 종속성이 6개월마다 꼬여서 엔터프라이즈 백엔드는 스프링 부트로 하고 추론 엔진만 FastAPI로 한다고. 지금까지 FastAPI로 뭐든 만들 수 있다고만 생각했는데 역할이 정해져 있다는 게 새로웠다.

### 3-1. 핵심 질문 1) Lazy vs Eager (Day1)

같은 20거래일 입력으로 모드마다 서버를 새로 띄워 3번씩 쟀다. 시작 시간은 프로세스 실행부터 `/health` 200까지, 요청 시간은 `/predict`를 연속 2번.

| 항목 | Lazy (평균) | Eager (평균) |
|---|---|---|
| 서버 시작 | 0.27 s | 2.82 s |
| 첫 /predict | 3.11 s | 0.18 s |
| 두 번째 /predict | 0.024 s | 0.018 s |
| 시작 직후 /health | model_loaded: false | model_loaded: true |

원시값 (3회)

| mode | run | 시작 | 첫 요청 | 두 번째 |
|---|---|---|---|---|
| lazy | 1 | 0.308 | 4.149 | 0.024 |
| lazy | 2 | 0.259 | 2.856 | 0.022 |
| lazy | 3 | 0.253 | 2.333 | 0.025 |
| eager | 1 | 2.267 | 0.172 | 0.018 |
| eager | 2 | 3.095 | 0.180 | 0.018 |
| eager | 3 | 3.104 | 0.185 | 0.017 |

해석. 모델 로드 비용 2~3초는 없어지지 않는다. 누가 내느냐가 다를 뿐이다. Lazy는 첫 사용자가 내고 Eager는 서버가 뜰 때 낸다. 시작과 첫 요청을 합치면 Lazy 3.38초, Eager 3.00초로 비슷하다.

Eager인데도 첫 요청이 0.18초로 두 번째 0.018초보다 10배 느린 게 이상했다. 모델 파일은 이미 읽었는데 왜 느리지 싶었는데, TensorFlow가 첫 `predict()` 호출 때 연산 그래프를 준비하는 것 같다. 기동 시 더미 입력으로 한 번 예측해 두면 없어질 거라고 본다.

실제 서비스라면. 교수님이 "정답은 없고 상황에 따라 다르다"고 하셨는데 측정해 보니까 기준이 생겼다. 컨테이너나 쿠버네티스처럼 헬스체크 통과해야 트래픽 받는 환경이면 Eager다. 모델 파일이 깨져 있으면 뜨는 단계에서 바로 실패하니까 잘못된 버전이 트래픽 받기 전에 걸러진다. Day2 Dockerfile이 `LOADING_MODE=eager`인 이유도 그거다. 개발 중에 `--reload`로 자주 재시작하거나 어떤 모델을 쓸지 나중에 정해지는 경우는 Lazy다. 조별 과제에서도 컨테이너는 Eager, 로컬 개발은 Lazy로 갈랐다.

### 3-2. 핵심 질문 2) 학습 시점과 서빙 시점의 일치 (Day1)

왜 20거래일 시퀀스인가. 모델이 `Input(shape=(SEQ_LEN, 2))`로 학습됐기 때문이다. `PredictRequest`가 `data/features.SEQ_LEN`을 import해서 `min_length=max_length=20`으로 강제한다. 숫자를 스키마에 따로 적어 두면 나중에 입력 길이를 바꿀 때 한쪽만 바뀌어서 어긋난다. 19개를 보내면 모델까지 안 가고 422에서 끝난다.

왜 scaler.pkl은 Day1에 한 번만 fit하는가. 가중치가 Day1 min-max 기준(종가 105.61~195.17)으로 변환된 숫자에 맞춰 학습돼 있다. 중간에 다시 fit하면 같은 $190이 다른 숫자로 들어가서 가중치랑 안 맞는다. fine_tune도 의미를 잃는다. 빈칸 5가 `HAICScaler.load(SCALER_PATH)`인 이유다. 교수님이 "에러 없이 결과만 틀어지는 조용한 실패"라고 하신 자리가 바로 여기다. 다시 fit해도 에러는 안 난다.

### 3-3. 핵심 질문 3) 배포 게이트 (Day2)

게이트가 없다면. `_register_if_gate_passed()`는 `score <= RMSE_GATE`일 때만 Production으로 올린다. 이 한 줄이 없으면 학습 끝난 모든 버전이 Production이다. 잘 된 모델과 나쁜 모델을 못 가린다.

통과 못한 버전은. MLflow run으로 기록만 남고 Registry Production으로 안 올라간다. 서버는 `models:/HAIC_Predictor/Production`만 보니까 탈락한 버전은 서버 입장에서 없는 것과 같다. 기존 Production이 계속 서빙된다.

운영자에게 주는 가치. 배포하는 사람과 배포해도 되는지 판단하는 기준을 분리한다. 내 v1은 2.03으로 통과했는데 만약 $4를 넘겼으면 콘솔에 `[GATE FAILED]`만 찍히고 서비스는 그대로였을 것이다. 실패가 서비스 중단이 아니라 "아무 일도 안 일어남"으로 처리된다는 점이 좋았다.

### 3-4. 핵심 질문 4) 드리프트 판정 기준 (Day3)

윈도우와 임계값을 바꾸면. 윈도우를 5건처럼 짧게 잡으면 며칠 우연히 어긋나도 드리프트로 잡는다(오탐). 100건처럼 길게 잡으면 진짜 드리프트가 시작돼도 평균이 기준을 넘기까지 오래 걸린다(미탐). 임계값도 낮추면 오탐, 높이면 미탐. 21건은 한 달 거래일이라서 잡은 절충점이다.

실제 결과.

- 정상 배치 (변동성 1.2%): `{'status': 'ok'}`
- 드리프트 배치 (변동성 3배): `{'status': 'retrain_triggered', 'promoted': True, 'rmse': 1.47}`

여기서 한참 헷갈렸다. 응답의 `rmse: 1.47`을 보고 "1.47인데 왜 드리프트지?" 했다. 코드를 다시 보니 이 값은 드리프트 판정에 쓴 RMSE가 아니라 재학습 직후 게이트 재검증에 쓴 RMSE였다. 판정용 RMSE(`compute_rmse()`로 최근 21건 계산해서 $4 넘은 값)는 응답에 안 들어간다. 감지 오차와 재학습 평가 오차가 다른 값이라는 걸 숫자만 보고 넘어갈 뻔했다.

조별 과제에서는 임계값을 고정값으로 안 두고 검증 오차의 1.25배로 유도했다. 고정 8%를 썼더니 모델 평상시 오차가 8.3%라 매일 드리프트가 떴기 때문이다. HAIC는 $4 고정이라 이 문제가 안 보였는데 실제 데이터 넣으니 바로 나왔다.

### 3-5. 핵심 질문 5) 재학습 방식 (Day3)

scratch가 아니라 fine-tuning인 이유. 빈칸 10을 채우면서 직접 골라야 했다. 최근 21거래일에 창문 20일을 더한 41행으로 파라미터 1.6만 개짜리 LSTM을 처음부터 학습하면 샘플이 부족해서 불안정하다. 3년치로 학습된 Production 가중치에서 10 epoch만 이어서 배운다. 학습률도 1e-4로 base(1e-3)보다 낮게 둬서 기존에 배운 걸 크게 안 흔든다.

재학습 모델이 게이트를 못 넘으면. fine_tune도 Day2와 같은 `_register_if_gate_passed()`를 탄다. 떨어지면 기존 Production이 그대로 남고 서비스는 안 멈춘다. 빈칸 11이 "promoted일 때만 OK 로그"인 이유다. 재학습을 시도했다는 것과 서비스가 바뀌었다는 것은 다르다. 4-7 버그로 더 확실히 알았다.

**4-8. 응답의 rmse 1.47이 판정 RMSE인 줄 알았음**

def compute_rmse(recent_predictions):
    if not recent_predictions:
        return 0.0
    se = [(p["actual"] - p["predicted"]) ** 2 for p in recent_predictions]
    return math.sqrt(sum(se) / len(se))

def is_drift(recent_predictions):
    if len(recent_predictions) < WINDOW_SIZE:
        return False
    return compute_rmse(recent_predictions[-WINDOW_SIZE:]) > RMSE_THRESHOLD
```

recent_predictions[:] = recent_predictions[-21:]
```
빈칸 6에서 actual을 `prices[i + SEQ_LEN - 1]`로 잡으면 창문 마지막 날을 "맞힌" 셈이 돼서 RMSE가 비정상적으로 좋아진다. 주석의 질문대로 한 칸 차이가 look-ahead 누수다.

`retrain_trigger.py` (빈칸 9, 10, 11 + 4-7 수정분)
```python
rows = load_rows(latest_upload())[-(SEQ_LEN + 21):]     # 창문 20 + 정답 21 = 41행
result = fine_tune(rows)                                  # warm start
if result["promoted"]:
    logger.info(f"[OK] new_rmse={result['rmse']:.2f} - production promoted: HAIC_Predictor v{result['version']}")
    model_loader.invalidate_cache()                       # 4-7: 안 비우면 예전 모델이 계속 응답
    return {"status": "retrain_triggered", "promoted": True, "rmse": result["rmse"]}
return {"status": "retrain_triggered", "promoted": False, "rmse": result["rmse"]}
```

## 6. 빈칸 정리 (이 줄이 없으면)

교수님이 "에러 없이 결과만 틀어지는 자리에 빈칸을 뒀다"고 하셔서, 채우면서 각 줄이 없으면 어떻게 되는지 같이 적었다.

| 빈칸 | 파일 | 채운 것 | 이 줄이 없으면 |
|---|---|---|---|
| 1 | train_baseline_v1.py | `model.fit(X_train, y_train_scaled, ...)` | test가 학습에 섞이면 RMSE가 실제보다 좋게 나온다 |
| 2 | model_loader.predict_one | `scaler.transform_point(close, volume)` | 정규화 안 된 원값이 들어가 의미 없는 값 |
| 3 | 위와 같음 | `scaler.inverse_close(pred_scaled)` | 0.47 같은 정규화 값이 그대로 응답 |
| 4 | model_loader.get_model | `if _model_cache is None:` | 매 요청 모델을 새로 읽어 2초씩 지연 |
| 5 | _load_from_mlflow | `HAICScaler.load(SCALER_PATH)` | 다시 fit하면 가중치 기준과 어긋남 |
| 6 | predict.batch_test | `prices[i:i+SEQ_LEN]`, `prices[i+SEQ_LEN]` | 한 칸 어긋나면 look-ahead 누수 |
| 7 | compute_rmse | `sqrt(mean((actual-predicted)**2))` | $4 비교가 틀어짐 |
| 8 | is_drift | `len(...) < WINDOW_SIZE → False` | 표본 1~2건으로 판단해 오탐 |
| 9 | retrain_trigger | `[-(SEQ_LEN + 21):]` | 21행만 자르면 학습 샘플 1개 |
| 10 | 위와 같음 | `fine_tune(rows)` | 41행 scratch 학습은 불안정 |
| 11 | 위와 같음 | `if result["promoted"]:` | 탈락한 모델도 성공 로그 |
| 추가 | retrain_trigger | `model_loader.invalidate_cache()` | 4-7. 로그는 성공인데 서빙은 안 바뀜 |

## 7. 전체 회고

**원래 알던 것.** FastAPI로 모델 감싸면 서비스가 된다 정도. MLflow는 이름만. 드리프트는 통계 시간에 분포가 바뀐다는 개념으로만.

**이번에 새로 배운 것.**

- Day1에서 서버가 떠 있는 것과 예측할 준비가 된 것이 다르다는 걸 Lazy 500 에러로 알았다. 헬스체크가 있다는 것과 헬스체크가 무엇을 확인하는지는 다른 문제다.
- Day2에서 버전이 추상적인 개념이 아니라는 걸 봤다. 내가 몇 번 돌렸는지가 v1, v3로 그대로 남는다. 게이트는 생각보다 단순했다. `if score <= 4.00` 한 줄. 복잡한 장치가 아니라 기준을 숫자로 명확히 정해 두는 게 핵심이었다.
- Day3가 제일 인상 깊었다. 4-7 캐시 문제는 처음엔 빈칸을 잘못 채운 줄 알았는데, 원인은 모듈 사이의 빈틈이었다. 로그를 찍는 모듈과 모델을 들고 있는 모듈이 서로를 몰랐다. 실습가이드가 로그 확인에서 끝내지 않고 재배포 후 `/predict` 응답까지 확인하라고 한 이유를 이해했다.
- 교수님이 "왜 필요하지, 이 위치에서 이 요소 기술이 어떻게 연결되지를 끊임없이 물으면서 가라"고 하셨는데, 빈칸이 정확히 그 자리에 있었다. 문법을 몰라서 못 채우는 빈칸은 없었고, 왜 이 값이어야 하는지를 모르면 틀리게 채워도 돌아가는 빈칸이었다.
- 포트 8000과 8077 같은 사소한 설정이 3일 내내 발목을 잡았다. README, Dockerfile, 스크립트 상수가 같은 값을 보는지 먼저 확인하는 습관이 생겼다.

**조별 과제(해아림)에 가져간 것.**

HAIC 구조를 태양광 10곳의 다음 날 24시간 발전량 예측으로 옮겼다. 개인 실습에서 겪은 걸 처음부터 넣었다.

- 4-7 캐시 문제는 도메인을 바꿔도 똑같이 생기는 문제라 승격 직후 캐시를 비우고, 응답에 `production-v2` 같은 실제 버전 번호를 넣었다.
- 4-5 경고는 Stage 대신 alias(@champion)로 바꿔 해결했다.
- 재학습을 요청 안에서 동기로 돌리면 그동안 `/predict`가 멈춘다는 게 부록 8번에 있었다. 백그라운드 스레드로 분리하고 `/jobs/current`로 상태를 보게 했다. 학습 중에도 기존 버전으로 응답하는 걸 캡처로 남겼다.
- 게이트는 RMSE 고정값이 아니라 "제도 오차 8% 통과율 0.45 이상"으로 바꿨다. 기준선이 0.30이라 그 1.5배다. 드리프트 임계값도 검증 오차의 1.25배로 유도해서 모델이 바뀌면 자동으로 따라가게 했다.
- HAIC에서는 "오차 크면 재학습" 하나였는데, 실제 발전소 데이터를 넣어 보니 오차가 커지는 이유가 대부분 모델이 아니라 설비 고장이나 날씨였다. 그래서 재학습 전에 원인을 가르는 단계를 하나 끼웠다. 지난 1년 실제 데이터에서 이상은 세 건 다 설비 문제였고, 전부 재학습을 막는 게 맞는 판단이었다. 재학습 루프 자체는 모의 시나리오로 검증했다.
- Lazy/Eager는 조별 코드에서도 다시 쟀다. 컨테이너는 Eager, 개발은 Lazy. Docker 빌드도 Mac에서 직접 돌려서 healthy까지 확인했다.

**아직 모르는 것.** 재학습 검증셋이 6일(4곳 × 6일 = 24 발전소-일)인데 이게 충분한지 확신이 없다. 교수님 Q&A에도 "fine-tuning 후 게이트 RMSE는 믿을 만한가"가 있었다. 운영이라면 승격 뒤 며칠 섀도로 같이 돌려보는 단계가 더 필요할 것 같다. 그리고 황사처럼 지역이 동시에 떨어지는 날씨를 모델 드리프트로 오판할 가능성이 남아 있다.

**한 줄로.** 모델을 만드는 것과 모델이 계속 맞게 운영하는 것은 다른 일이고, 그 사이를 잇는 게 서빙, 게이트, 감시, 재학습이라는 네 개의 선이었다.
